## Design Specificity Verdict

**LLM assessment:** Strongly authored for Nudge. The black/concrete/yellow Clear Signal language, four-step workout rail, oversized action planes, timers, and numbered exercise rows form a coherent visual world tied to training around equipment. The active workout and cooldown screens could not be transplanted unchanged into an unrelated product. Specificity weakens in Settings and empty History, where the experience becomes a conventional admin form/list and loses the journey’s decisive contextual guidance.

**Deterministic scan:** `detect.mjs --json src` exited 0 with zero findings. No rule names or file locations were emitted and there were no false positives. Spot checks confirmed intentional exceptions: circular journey markers, the current-step concentric ring, and CSS-drawn History disclosure glyphs support state rather than generic decoration.

**Visual overlays:** No reliable user-visible overlay is available. Mutable injection failed: the attempted title change did not persist and no marker script appeared. The detector live server was therefore not started and no overlay is claimed. Manual rendered inspection plus the clean CLI scan supplied the fallback evidence.

## Overall Impression

Nudge’s core workout journey is unusually coherent: it feels like a purpose-built operating interface for someone training around equipment, not a generic form app. The biggest opportunity is to let that excellent hierarchy survive the repetitive, phone-held active-set loop. Right now the shell, journey rail, and focus transfer push the next required control almost below the fold at precisely the moment speed matters most.

## What’s Working

- **The one-signal hierarchy is disciplined.** Yellow consistently identifies the next worthwhile action, while black planes establish state without card clutter.
- **Workout recovery preserves agency.** Cancel timer, Start set early, Continue workout, early-finish inventory, and Back to workout cover realistic interruptions without motivational theater.
- **Accessibility foundations are strong.** The rendered flow has one H1, logical heading structure, native controls, explicit labels, 44px-plus targets, visible focus, semantic regions/tables, live announcements, and reduced-motion support.

## Cognitive Load

Moderate: two of eight checklist areas fail. Grouping, hierarchy, progressive disclosure, working-memory support, chunking, and the one-thing-at-a-time journey are effective. Single focus and minimal choices break down in Settings/catalog and workout-order editing.

- Plan exposes five local manipulables, but the dominant action remains obvious.
- Workout ready begins with two decisions, then adds four exercise expanders and up to eight Earlier/Later controls.
- Settings begins with four job links, three catalog filters, Add exercise, and repeated Edit/Deactivate actions across 15 exercises.
- Active-set work stays near four controls, but Confirm attempt began around `y=806` in an approximately `846px` viewport after focus moved to the phase heading.

## Emotional Journey

- **Entry:** calm and competent. “45 min” and restrained instruction make planning feel bounded.
- **Anticipation:** “Workout ready” and the yellow Start workout plane create a clear commitment moment, though the Plan-highlighted rail weakens state confidence.
- **Peak:** Start set and post-set Rest are excellent. Set progression, explanation, remaining timer, and Start set early feel purposeful.
- **Valley:** immediately after starting the first set, focus/scroll returns to “Main workout,” leaving Confirm attempt nearly below the fold. This inserts friction into the most repetitive action.
- **High-stakes reassurance:** early finish is handled exceptionally well through an explicit unfinished-work inventory and Return to workout escape.
- **End:** Review is a strong factual receipt. Post-save closure was not assessed.

## Priority Issues

### 1. [P1] Repeated active-set confirmation falls below the phone fold

**Why it matters:** After Start set changes the phase to Main workout, `WorkoutView.jsx` focuses the phase heading. At the tested phone viewport, Confirm attempt began around `y=806`, forcing the trainee to scroll before completing a set. Repeating that across a 16-set workout turns a small layout defect into persistent gym-floor friction and separates keyboard or screen-reader focus from the next required control.

**Fix:** Preserve focus and scroll at the active set when work starts, announce the phase transition through the existing live region, and keep Confirm attempt fully visible. Evaluate a compact active-workout shell while retaining safe, labeled navigation.

**Suggested command:** `$impeccable adapt src/components/WorkoutView.jsx`

### 2. [P2] Settings defaults do not compose cleanly on mobile

**Why it matters:** Labels and controls such as “Warmup minutes 10” visually run together. The semantics are correct, but the mobile layout feels like an unfinished admin form and slows scanning.

**Fix:** Make each `.setting-group label` an explicit grid with a clear gap; give number/select controls a deliberate full or bounded width; keep save hints directly beneath their field.

**Suggested command:** `$impeccable layout src/components/Settings.jsx`

### 3. [P2] “Workout ready” reports two different current phases

**Why it matters:** The shell says Workout and the heading says Workout ready, while the journey rail still highlights Plan. A user should not have to decide whether generation completed planning or began the workout.

**Fix:** Choose one state model: either label the screen as final Plan confirmation everywhere or advance the rail to Workout. Use one name and one active indicator.

**Suggested command:** `$impeccable clarify src/components/WorkoutView.jsx`

### 4. [P2] History empty states are factual but dead-ended

**Why it matters:** Workouts says “No workouts logged yet.” Exercises autofocuses an unusable filter above “No eligible exercises in the last year.” First-time users receive neither a useful action nor an explanation of the product loop.

**Fix:** Hide the exercise filter until eligible data exists. Explain that completing and saving a workout populates History and Trends, then provide a direct Plan action or clearly contextualized shell action.

**Suggested command:** `$impeccable onboard src/components/WorkoutHistory.jsx`

## Persona Red Flags

**Casey, distracted mobile user:** The 2×2 global navigation and journey rail consume substantial vertical space during exercise. Confirm attempt is nearly below the fold after the phase transition, creating repeated scrolling across a multi-set plan.

**Sam, accessibility-dependent user:** Semantic structure and visible focus are excellent. The failure is focus destination: moving to the phase heading after Start set separates keyboard and screen-reader users from the control they need next.

**Jordan, first-timer:** The Plan/Workout contradiction at Workout ready and phrases such as “eligible exercises” require interpretation. Empty History offers no explanation of how to create the first record.

## Minor Observations

- Lowercase “actual weight” and “actual reps” read less finished than the otherwise disciplined label system.
- Four equally weighted shell actions make Sign out as visually available as Plan/Workout on a high-frequency mobile surface.
- The programmatic blue outline around headings is useful focus feedback but visually dominant; reserve it for necessary focus transfers.
- The early-finish unfinished-work list becomes internally scrollable on phone; protection is appropriate, though Continue can fall well below the initial view.
- At the desktop assessment’s effective `1082×676` CSS viewport, the primary yellow Plan action began below the fold. The requested `1440×900` override was not honored exactly, so treat this as a scaling-specific signal requiring confirmation rather than a universal desktop defect.

## Questions to Consider

- Could active workout mode become a deliberately reduced “training cockpit” while keeping History and Settings safely reachable?
- Is Workout ready still planning, or has the user already entered the workout? The interface currently answers both ways.
- Should an empty History teach the product loop instead of presenting controls that cannot yet produce a result?
